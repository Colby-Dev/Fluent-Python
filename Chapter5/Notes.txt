

   Chapter 5: Data Class Builders
   ==============================


   Data classes are a collection of fields with little or no extra functionality such as a decorator or using libraries like collections.namedtuple or typing.NamingTuple.

   Using Data classes helps reduce code and simply objects that are returned. For example if an object holds coordinates using comparison operators will only compare the hashable object to the other value which may look right but will not return a True unless its the same object. 

   To get around this we use a Data Class. In Example 1, we show how to use a few data classes to address this issue with python. This allows for simple conversions and uses of data despite it being in an object field and reduces the amount of code. 

   (see Example 1) 

   > Main Features of These Data Builders
   --------------------------------------

	Mutable Instances - using typing.NamedTuple and 
			    collections.namedtuple are tuple subclasses so 
			    they are immutable. @dataclass produces mutable
			    classes. @dataclass can use a frozen arg that 
			    when True raises an exception if you try to 
			    assign a value to a field after initialization.

	Class Statement syntax - typing.NamedTuple and @dataclass support 
				 regular class statement syntax. This 
				 makes it easier to add methods and 
				 docstrings. 

	Construct dict - both named tuple variants provide an instance 
			 method (._asdict) to make a dict object from 
			 the fields in the instance of the tuples. 
			 @dataclass has dataclasses.asdict. 

	Field names & default values - all class builders let you get 
				       field names and default values. 
				       You can get this metadata from the 
				       tuples by using ._fields and 
				       ._fields_defaults class attributes. 
				       From the dataclasses module you can 
				       use the fields function which 
				       returns a tuple of the fields.

	Get Fields Types - You can use the .get_type_hints function to 
			   find the class attributes instead of reading 
			   from the __annotations__ of the data classes. 

	New Instance with Changes - given a named tuple instance x, the 
				    call x._replace(**kwargs) returns a
				    new instance with the kwargs given. 
				    dataclass does the same. 

	New Class at Runtime - Using class syntax is readable but it is
			       hardcoded. A framework may need to create
			       new data classes at runtime though. named
			       tuples allow you to do this by default and
			       data classes uses a make_dataclass function
			       to do this. 

   > Classic Named Tuples
   ----------------------

   	The collections.namedtuple function is a factory that builds subclasses of tuples with different fields, and unique __repr__ . Classes built with namedtuple can be used where tuples are needed, so basically immutable objects. Some of the most useful things with namedtuples is the ability to transform them to dict, gather fields, and creating specific data types / other data structures like tuples inside of namedtuple. Named tuples offer a few attributes and methods in addition to those inherited from a tuple class. 

	(see Example 2)

	Namedtuple accepts a defaults keyword which provides default values to attributes. This allows the function signature to specify default values regardless of the variables passed. You can also do this with classes. 

   > Typed Named Tuples
   --------------------

   	Any class with a default field can be written using typing.NamedTuple to define attributes that the class will have regardless. These classes do not have any methods other than the ones from the collections.namedtuple. The best part of these classes are type annotations (type hints) dicussed next. 

   > Type Hints 101
   ----------------

	Type hints are ways to delcare the expected types of function args, return values, variables, and attributes. Type hints are documentation that can be checked by IDEs since they have no behavior at runtime. Thus, creating a program that uses a float type hint can still except other types since they have no actionable purpose at runtime.

   > Variable Annotations
   ----------------------
	
	When using type hinting no effect happens at runtime, except if modules used call for it. Most modules that do use the __annotations__ method which the modules typing.NamedTuple and @dataclass use to allow for extra functionality. The __annotations__ method builds a dictionary of the attributes in the class and their type hinted values. They do not observe constant default values as shown in Example 3. 

	(see Example 3)

	As you can see the behavior is similar but one important note is that the Dataclass is mutable while the NamedTuple is not. NamedTuple is a subclass of Tuple so it inherits the basic dunder methods, whereas @dataclass can has some parameters that can change the dunder methods. 

   > Field Options
   ---------------

   	In Python, default fields are all or nothing. If you specify the params with defaults then you must supply all variables in the function signature for NamedTuples whereas Dataclass does not need this. Using defaults is very useful as we can type hint the default params to classes that way when we create a new instance of the class it will make new variables specific to that instance, instead of all instances sharing the same list. 

	(see Example 4)

   > Post init Processing
   ----------------------

	The __init__ method that is created from @dataclass only takes arguments passed and then assigns them. @Dataclass can also use __post_init__ for validation and computer field values based on other fields. __post_init__ can hold code that will execute based on initialization of classs. This can be useful to check values or instantly compute some after initialization.

   > Pattern Matching Class:
   -------------------------

   	Class patterns are designed to match class instances by type and attributes. There are 3 types of class pattern matching: simple, keyword, and positional. This is a perfect use case of @dataclass or typing.NamedTuple because we can uniformly establish what the classes look like with tuples and use their class specific attributes. 

   > Simple Method:
   ----------------

	Using simple method you can specify the type and which attributes to grab out of the pattern. For example: 

		case [str(name), _, _, (float(lat), (float(lon)))]

	This would speciy name is a string, then have two garbage variables, finally have a float tuple of lat and lon. 

   > Keyword Class Pattern
   -----------------------

   	Keyword class patterns match specific keywords in a class attributes to return specific results. This can be done by matching common fields that are uniform for the instance of the class then appending them to a result like a list. As long as the attribute we are matching for qualifies it will return the result regardless of the other fields. 

	(see Example 6)

   > Positional Class Pattern
   --------------------------

   	In the past Example 6 we wanted to return the city name and continent for the match that we made. In doing so we had to use an f string and dig into the variable which can be verbose in the code base. A simpler way of doing this is using the garbage variable _ to take the arguments we dont want. 

	This is helpful because now we can just use the case and just have a place for the continent variable and any other variable we are trying to show from the match case. Here is an example: 

		match city:
			case City('BRLN', _ , continent) 
			results.append(city.continent) 

   	You can always find the positonal arguments by using the __match_args__ variable to show the order of the args.
